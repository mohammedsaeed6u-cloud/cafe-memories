# STAMPY — دليل المكتبات والأدوات الاحترافية

**القاعدة:** استخدم الموجود، أثبت الاحتياج، ثم أضف أقل dependency ممكن. هذا الدليل لا يثبت حزمًا جديدة ولا يضمن توافق أحدث إصداراتها؛ يجب فحص peer dependencies وruntime والترخيص والحجم قبل الإضافة.

## 1. الموجود فعلياً حسب package.json وقت إعداد الحزمة

| المكتبة | الاستخدام المناسب | ضابط الاستخدام |
|---|---|---|
| Next.js 16 + React 19 | واجهات ومسارات خادمية | اقرأ docs النسخة المثبتة؛ لا تعتمد على معرفة إصدار قديم |
| TypeScript | عقود وأنواع | أنواع DB/API دقيقة؛ لا any كاختصار |
| Tailwind CSS v4 | tokens وتنسيق responsive | رموز دلالية بدلاً من hex موزع |
| @ark-ui/react | Dialog/Tabs/Select وعناصر تفاعلية | أعد استعمال primitives بدلاً من صنع modal غير متاح |
| lucide-react | أيقونات موحدة | لا تستخدمها كبديل للنص أو labels |
| clsx + tailwind-merge + CVA | تركيب classes وvariants | مكونات موحدة لا نسخ أزرار مختلفة لكل صفحة |
| react-hook-form + Zod + resolvers | نماذج وتحقق | التحقق يعاد على الخادم؛ العميل وحده لا يحمي API |

| better-auth | موجود كاعتمادية للمصادقة | لا تفترض أنه المصدر الفعلي لكل الجلسات؛ تتبع التنفيذ قبل أي تغيير |

| OpenNext/Cloudflare/Wrangler | بناء ونشر | الاعتمادية لا تعني أن backend نُشر أو أن المحول متوافق |

## 2. الإضافات المقترحة بالترتيب

### أ. @playwright/test — أولوية مرتفعة عند بدء اختبار المتصفح

**الفائدة:** رحلات عبر أجهزة browser contexts، لقطات مقارنة، والتحقق من الحفظ بعد إعادة التحميل.

**الحالات الأولى:** إنشاء منشأة، دخول موظف، تسجيل زيارة، فتح الكارت من جلسة ضيف، ألبوم خاص، إنشاء حملة وقراءتها، ومحاولة عبور منشأة.

**شروط:** بيانات staging أو fixtures معزولة، أسرار في CI، تنظيف مدروس، وعدم تنفيذ حملات حقيقية ضمن اختبار عادي. تثبيت الحزمة لا يثبت browser binaries؛ إعدادها مرحلة منفصلة. لا نقبل retries تخفي عيباً ثابتاً.

### ب. @axe-core/playwright — مع Playwright

**الفائدة:** فحص آلي لجزء من مشاكل الإتاحة.

**الحدود:** لا يغني عن لوحة المفاتيح وقارئ الشاشة والتباين اليدوي والسياق البصري. نجاح axe لا يساوي شهادة WCAG.

### ج. MSW — عند تكرار اختبارات HTTP وحالات الفشل

**الفائدة:** محاكاة ردود الشبكة من الاختبار دون إدخال mock success داخل API الإنتاجي.

**الحدود:** mock لا يثبت RLS أو SQL أو المزوّد. اجعل سيناريوهات 401/403/500/timeout جزءاً من fixtures. امنع تفعيل mocks في production.

### د. @sentry/nextjs أو خدمة مراقبة مناسبة للاستضافة — بعد حسم النشر

**الفائدة:** أخطاء runtime وrequest correlation وتتبع الإصدار.

**الضوابط:** فحص دعم runtime، تنقيح PII، إيقاف تسجيل الصور وحقول الهاتف والتوكنات، وضبط sampling والكلفة. لا تفعل session replay تلقائياً في صفحات الضيوف والصور.

## 3. إضافات مشروطة وليست مطلوبة الآن

| المكتبة/الأداة | متى تصبح مناسبة؟ | متى نرفضها؟ |
|---|---|---|
| @tanstack/react-query | بيانات عميل مشتركة، caching وinvalidations متكررة ومعقدة | صفحة بسيطة أو إذا كانت ستكرر caching Server Components بلا تصميم |
| @tanstack/react-table | جداول CRM مع فرز/إظهار أعمدة مضبوط | إذا كانت ستستخدم لتبرير تحميل كل العملاء محلياً |
| Recharts | مؤشرات حقيقية تحتاج رسوماً بسيطة | بيانات وهمية أو dashboard يمكن شرحه بأرقام أقل |
| motion | تفاعل مميز لا يغطيه CSS بسهولة | لتحريك كل الشاشة أو قبل تثبيت الأداء وتقليل الحركة |
| date-fns | معالجة تواريخ متقدمة أو قواعد زمنية متكررة | تنسيق بسيط يحققه Intl؛ حدد timezone في كل الحالتين |
| Storybook | مكتبة مكونات مشتركة وفريق يحتاج مراجعة معزولة | إذا كان سيستهلك وقتاً دون مكونات مستقرة أو مالك صيانة |
| pgTAP | فريق يشغّل اختبارات SQL ضد Postgres فعلي | كبديل شكلي عن الاختبارات الموجودة دون فائدة واضحة |
| أدوات طابور مزوّد الاستضافة | تجاوز المهل أو أحمال ووظائف خلفية مثبتة | بنية Redis/BullMQ داخل runtime غير متوافق أو بلا حاجة |

## 4. ما لا أوصي بإضافته تلقائياً

- Radix/shadcn بالتوازي مع Ark UI لمجرد أن المرجع يقترحهما؛ الهجرة قرار له تكلفة وإتاحة واختبارات.
- Prisma/Drizzle لمجرد وجود Supabase؛ لا نحتاج طبقة ORM إضافية دون مشكلة محددة.
- نظام auth ثالث أو تبديل auth في مهمة تصميم.
- مكتبة صور ضخمة إن كانت القدرات الحالية وsharp تكفي.
- مكتبة animations وcarousel لكل شاشة؛ CSS يكفي لكثير من التفاعلات.
- Stripe أو مزوّد دفع قبل اعتماد السوق والفوترة والعقود وإعدادات webhooks.
- تكامل Apple/Google مباشر بالتوازي مع Wallet provider بلا استراتيجية واضحة.
- MCP servers عشوائية تمنح وصول DB أو filesystem أو نشر بلا حدود صلاحية.

## 5. بروتوكول إدخال dependency

1. حدد المشكلة التي لم يحلها الموجود.
2. راجع package.json وlockfile واستعمالات الحزم الحالية.
3. تحقق من اسم الحزمة ومصدرها ونسختها وترخيصها ودعم React/Next/runtime.
4. قارن dependency بكلفة implementation صغير وآمن.
5. اعرض تأثير bundle وCI والأسرار والتشغيل قدر الإمكان؛ لا تخترع أرقاماً.
6. أضف حزمة واحدة في تغيير واضح وحدّث lockfile بمدير الحزم المعتمد.
7. شغّل النوع والاختبارات والبناء المعني، وأضف مثالاً واقعيًا واحداً قبل التوسع.
8. وثق سبب القرار وكيفية إزالتها إن لم تعد مطلوبة.

## 6. أدوات harness والاتصالات

- **Git/GitHub:** قراءة diff وchecks وPR؛ لا merge أو نشر بلا إذن.
- **Linear:** مهمة محددة ومعايير قبول وأدلة، لا تحديث done تلقائي عند أول commit.
- **Browser tooling:** يبدأ بخادم محلي متاح في نفس البيئة أو URL معاينة؛ localhost جهاز آخر ليس جهاز الوكيل.
- **Supabase tools إن توفرت:** مشروع staging محدود، قراءة schema قبل mutation، وعدم استخدام الإنتاج كملعب تجربة.
- **Terminal:** أوامر قصيرة قابلة للتتبع؛ عملية server طويلة عبر أداة background مناسبة إن كانت متاحة.

توفر الأدوات يعتمد على البيئة الفعلية. هذه قائمة صلاحيات واستخدامات مقترحة، لا ادعاء أن كل integrations متصلة.

## 7. الاختيار المختصر

**نستخدم الآن:** stack المشروع + المهارات الأربع + اختبارات رجوع.

**أول إضافة مفيدة غالباً:** Playwright، ثم axe عند وجود تجهيز متصفح وبيئة اختبار.

**بعدها حسب الاحتياج:** MSW لاختبارات الشبكة، ومراقبة أخطاء متوافقة مع النشر.

**نؤجل:** إعادة بناء stack أو microservices أو بنية 100M مستخدم حتى يوجد قياس وحاجة مثبتة.
