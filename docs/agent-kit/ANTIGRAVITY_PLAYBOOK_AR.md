# STAMPY — عقد عمل Antigravity وحزمة المهارات

**الإصدار:** 1.0 — 24 أكتوبر 2026
**الغرض:** تقليل التوهان، منع النجاح الصوري، ضبط العمل المتوازي، وتحويل كل مهمة إلى تغيير محدود يمكن التحقق منه.

> هذه قواعد تشغيل للمشروع وليست تعديلاً لمحرك Antigravity نفسه. ملفات Markdown لا تضمن الالتزام آلياً؛ يجب تفعيل القراءة في الأداة المستخدمة وربط القواعد بفحوص CI ومراجعة بشرية. لا ندعي أن تثبيت المهارات يحسّن المنتج دون استعمالها والتحقق من نتائجها.

## 1. التشغيل السريع

1. افتح المستودع الصحيح واقرأ `AGENTS.md` و`GEMINI.md` ثم هذه الوثيقة.
2. اقرأ ملف المهارة المناسب من `.agents/skills/`؛ لا تعتمد على أن واجهة الأداة اكتشفتها تلقائياً.
3. ابدأ بـ`stampy-task-control` في كل مهمة؛ استخدم المهارات الثلاث الأخرى حسب النطاق.
4. انسخ قالب المهمة أدناه في Linear أو سجل العمل.
5. نفّذ شريحة واحدة، اختبر، راجع diff، وسلم بدليل.

إن لم يدعم harness اكتشاف SKILL.md، مرر مسارات الملفات صراحة ضمن prompt. لا توجد حاجة لتثبيت حزمة npm لهذه المهارات المحلية.

## 2. قواعد لا تفاوض عليها

### 2.1 الحقيقة قبل الثقة
- لا تقل «اشتغل» لأن زميل قال ذلك؛ افحص النسخة الحالية.
- لا تقل «100%»؛ اذكر ما اختبرته تحديداً وما لم تختبره.
- لا تقل إنك فتحت المتصفح إذا قرأت JSX فقط.
- لا تقل إنك نشرت إذا بنيت محلياً فقط.
- لا تسجل أعداد اختبارات قديمة كأنها نتائج اليوم.
- لا تدعِ تشغيل وكلاء فرعيين دون أداة فعلية ونتائج منهم.

### 2.2 حماية العمل
- لا تمسح تغييرات شخص آخر ولا تستخدم reset/clean لتسهيل الدمج.
- احترم فرع الجلسة والنطاق المحجوز؛ لا تدفع إلى main مباشرة.
- اقرأ status قبل أي مزامنة. عند التغييرات غير المفهومة توقف وحدد صاحبها أو احفظها بطريقة مصرح بها.
- الملفات المشتركة مثل globals/auth/schema تحتاج تنسيقاً قبل تعديلها.
- لا تجمع refactor واسعاً وتغيير منتج وإصلاح أمان في مهمة واحدة.

### 2.3 منع الاختصارات الخطرة
- ممنوع نجاح وهمي عند فشل DB أو المزوّد.
- ممنوع ثابت `walletMarketingOptIn: true` كبديل لقراءة الموافقة.
- ممنوع bypass للمصادقة داخل كود الإنتاج بحجة الاختبارات.
- ممنوع `as any` أو ts-ignore كحل افتراضي؛ وضّح الحدود ونمذج الأنواع.
- ممنوع catch فارغ أو إخفاء الخطأ كقائمة فارغة.
- ممنوع إضافة مكتبة لمجرد أن skill ذكرها.
- ممنوع تنفيذ نشر أو ترحيل إنتاجي تلقائياً لمجرد إنهاء مهمة.

## 3. دورة التنفيذ الإلزامية

### افهم
اقرأ الهدف والملفات والعقود والمخطط والاختبارات. سجل commit ونطاق العمل. ابحث عن التنفيذ الموجود قبل بناء بديل.

### اتفق
حدد القبول وغير الأهداف. إذا اختلفت الوثائق مع الكود أو قرارات الخصوصية، اطلب حسم القرار المؤثر بدلاً من اختراعه.

### اختبر العيب
اكتب حالة إعادة إنتاج أو regression. يفضل إظهار فشلها قبل الإصلاح. إن كان ذلك غير عملي، وثق السبب ولا تدّعِ red/green لم يحدث.

### نفذ
أقل تغيير صحيح، مع طبقات واضحة وعقد ثابت. لا توسع الصلاحيات أو تدخل تخزيناً محلياً كمصدر حقيقة لتجاوز صعوبة الربط.

### تحقق
تشغيل checks المناسبة، مراجعة diff، حالات سلبية وتزامن عند الحاجة. بعد آخر تعديل أعد الفحوص المتأثرة؛ لا تستخدم نتيجة سابقة لتعديل أحدث.

### سلّم
ملخص، ملفات، أوامر ونتائج، حدود، ومتطلبات البيئة. حدث Linear ولا تغلق قبولاً يتطلب جهازاً أو staging لم يُختبر.

## 6. المهارات المحلية الجديدة

| المهارة | متى تستخدم | الناتج المطلوب |
|---|---|---|
| stampy-task-control | بداية كل مهمة أو استعادة سياق | عقد مهمة ونطاق واضح |
| stampy-operational-integrity | CRM/حملات/أختام/مكافآت/صلاحيات | ثوابت أعمال واختبارات عزل وفشل |
| stampy-ui-review | تعديل أو مراجعة واجهة | حالات UI وRTL وإتاحة ودليل بصري إن أمكن |
| stampy-release-evidence | قبل التسليم أو الإطلاق | سجل أدلة وحدود تحقق |

### مهارات موجودة مفيدة بالفعل

- `clean-code-guard`: مراجعة جودة diff بعد التنفيذ.
- `test-guard`: مراجعة جودة الاختبارات وعدم الاكتفاء بمطابقة نصوص المصدر.
- `supabase-postgres-best-practices`: SQL والفهارس والأداء؛ يقرأ الجزء المناسب للمهمة.
- `supabase`: إرشادات قاعدة البيانات ضمن ما يتيحه runtime فعلياً.
- `ui-ux-pro-max`: مرجع UX وتخطيط، لا سلطة لتغيير هوية STAMPY.
- `docs-guard`: مراجعة توثيق المهمة عند انطباق تعليماته.
- `saas-delegator`: قائمة أدوار للتنسيق عند الحاجة، لا مبرر لإنشاء بنية 100 مليون مستخدم أو ضمان زمن استجابة بلا قياس.

### مهارات لا تُفعّل عميانياً

- `shadcn-ui` ليست دليلاً على وجود Radix أو مكونات shadcn مثبتة. المشروع يستخدم Ark UI بالفعل؛ الحفاظ على stack الحالي هو الافتراضي.
- مهارات WordPress/WooCommerce لا تخص تطبيق Next.js هذا ما لم تظهر مهمة تكامل محددة.
- تشغيل عدة delegators معاً يزيد تضارب التعليمات. منسق واحد يكفي، وتُقرأ تعليمات كل مهارة قبل استعمالها.
- بعض ملفات الإرشاد القديمة تصف ألواناً مختلفة أو متطلبات scale عامة. لا تحسم التعارض تلقائياً: قدّم قرار الهوية المعتمد وحدد التعارض لقائد الفريق، مع الالتزام بتعليمات الأداة الأعلى أولوية.

## 7. استخدام المكتبات بقرار هندسي

راجع `LIBRARY_DECISIONS_AR.md`. الاحترافية تأتي من صحة السلوك والاختبارات والإتاحة، لا عدد dependencies. لا ترقِّ مكتبة أو تستبدل نظام auth/UI أثناء إصلاح محدود دون قرار مستقل.

## 8. بروتوكول العمل الجماعي

- قائد المهمة يحدد العقد؛ صاحب backend يملك schema/API؛ صاحب الواجهة يستهلك عقداً معتمداً.
- لا يغير طرفان الملف نفسه بالتوازي دون تنسيق.
- العامل الفرعي يستلم: الهدف، الملفات، الممنوعات، العقد، الاختبارات وقالب التسليم.
- المراجع لا يعتمد كلام المنفذ؛ يراجع diff والنتائج.
- المنسق يختبر النسخة المدمجة، فلا يكفي نجاح كل فرع بمفرده.
- عند عيب خارج النطاق: وثقه ولا تنفذ إصلاحاً واسعاً دون موافقة.

## 9. الأدلة المطلوبة حسب نوع الادعاء

| الادعاء | الحد الأدنى للدليل |
|---|---|
| TypeScript ناجح | الأمر وexit code بعد آخر تعديل |
| الاختبارات ناجحة | عدد فعلي ومجموعات مشغلة ونسخة |
| UI معتمد | معاينة وتفاعلات وviewport وحالات، لا screenshot واحد فقط |
| العزل آمن ضمن الاختبار | حالات مستخدمين ومنشأتين وفروع مع سياسات DB |
| حفظ دائم | إنشاء ثم قراءة بعد إعادة التحميل/جلسة جديدة |
| Wallet يعمل | بيئة مزوّد وجهاز مناسب، مع فصل الإصدار والتثبيت والتحديث |
| منشور | artifact/commit وبيئة ورابط وsmoke موثق |

## 10. أوامر تحقق للمشروع

تحقق من scripts وpackageManager أولاً. إذا كان pnpm المثبت لا يطابق lockfile فلا تعالجه بتحديث شامل صامت.

```bash
git branch --show-current
git status --short
pnpm install --frozen-lockfile
pnpm exec tsc --noEmit
pnpm lint
pnpm test
git diff --check
# عند تغيير runtime/build أو اعتماد إصدار:
pnpm build
```

هذه قائمة أوامر وليست ادعاء بأنها نُفذت في هذه المهمة. إذا فشل التثبيت بسبب peer dependencies افحص التعارض ولا تستخدم force كحل تلقائي. لا تتخطَّ فحوصاً ثم تعلن نتيجة كاملة.

## 11. الحماية الآلية المطلوبة تدريجياً

- CI يفشل على type errors وlint errors وtests الفاشلة.
- regression tests لغياب المصادقة في نفس test environment بدلاً من كود bypass.
- اختبارات سلبية للعزل والموافقة.
- مراجعة migrations قبل التطبيق.
- فحص أسرار ضمن workflow مناسب، مع تنقيح الأدلة.
- branch protection ومراجعة PR عندما تسمح خطة GitHub وإعدادات الفريق.
- لا تضف regex يمنع كلمات عامة مثل true أو any في كل الملفات؛ استخدم قواعد دقيقة واختبارات سلوك لتقليل false positives.

## 12. Prompt جاهز لإرساله إلى Antigravity

```text
أنت تعمل على STAMPY. قبل التنفيذ اقرأ AGENTS.md وGEMINI.md ثم:
docs/agent-kit/ANTIGRAVITY_PLAYBOOK_AR.md
واقرأ .agents/skills/stampy-task-control/SKILL.md.

اعرض أولاً عقد المهمة: الهدف، الفرع والنسخة، الملفات، غير الأهداف، ومعايير القبول.
اختر فقط المهارات المرتبطة بالنطاق. لا تغير stack أو هوية أو قواعد موافقة دون قرار صريح.
لا تستخدم demo fallback أو test-mode auth bypass أو ادعاءات نجاح غير مثبتة.
اكتب regression للعيب، نفذ أقل تعديل صحيح، وافحص الحالات السلبية.
قبل التسليم اقرأ stampy-release-evidence وشغّل الفحوص المتاحة بعد آخر تعديل.
سلّم: ما تغير، الأدلة، ما لم يُختبر، وما يحتاج staging أو جهازاً حقيقياً.
إذا تعارضت التعليمات أو غاب قرار حساس، توقف واسأل بدلاً من اختراع سياسة.
المهمة الحالية: [ضع مهمة واحدة محددة هنا].
```

## 13. قياس التزام الوكيل

لا نقيسه بكمية الكود. نقيس: هل التزم بالنطاق؟ هل اكتشف التعارض؟ هل منع فقد العمل؟ هل اختبر الفشل؟ هل كانت التقارير صادقة؟ وهل تكررت المشكلة بعد الإغلاق؟ راجع هذه النقاط بعد أول ثلاث مهام وحسّن القواعد القصيرة بدلاً من تكديس مئات الصفحات من التعليمات.
