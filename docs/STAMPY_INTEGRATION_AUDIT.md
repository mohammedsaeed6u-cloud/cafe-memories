## Security blockers in the STAMPY snapshot

1. **Unverified visits:** `src/app/api/v1/visits/route.ts` inserts visits via the service-role client using organization/customer/branch IDs supplied in the request; its in-process anti-fraud evaluation is not staff confirmation. STAMPY `00005_security_and_rls_hardening.sql` and `00006_production_complete.sql` also add permissive `WITH CHECK (true)` policies for visits. Preserve STAMPY's touch keypad and kiosk presentation, but bind their actions to the authenticated staff-confirmed `record_verified_visit` RPC with an idempotency key.
2. **Photo privacy:** `src/app/api/v1/memories/route.ts` accepts arbitrary image URLs, identity IDs and consent flags. STAMPY's SQL allows public memory insertion and broad reads. Private guest photos must be created by the signed-in owner against a verified visit, stored privately, and visible to a merchant only after explicit wall submission; the display additionally needs approval and per-request authorization.
3. **Browser authority:** STAMPY uses `localStorage` for stamp/redemption ledgers, photo/consent state, screen pairing and staff-facing counters (for example `src/features/terminal/hooks/useTerminalCashier.ts` and `src/features/customer-experience/hooks/useCustomerExperience.ts`). Local storage may retain presentation preferences, but it must not authorize a visit, staff role, wallet pass, consent, or reward.
4. **Accounts and secrets:** STAMPY's `src/lib/auth/auth.ts` has a fallback static secret and no shared Supabase Auth identity for existing guest accounts. `00006_production_complete.sql` seeds a demo organization and stores `tenant_wallet_quotas.wallet_api_key` as plaintext; other RLS policies expose wallet links. Do not deploy the seed or copy plaintext keys. Migrate existing Wallet credentials only via secure re-entry/rotation and encrypted server-only connectors; keep Google/Supabase account access intact.
5. **Migration-number collisions:** STAMPY already has different migrations named `00003`–`00006`. Copying the secure branch's `00003_secure_core.sql`, `00004_customer_accounts.sql`, `00005_visit_keepsakes.sql`, `00006_brand_wallet_privacy.sql` into it under those numbers is neither append-only nor correct. On a development Supabase copy, audit current schema and data, adapt them to STAMPY's table/policy changes, then append `00007+` without rewriting applied migrations. Test the full chain with PGlite and live staging RLS before rollout.
6. **Hosting:** STAMPY's `wrangler.jsonc` points to static `out`, and its optional `STATIC_EXPORT` disables the API routes. Simply restoring the Edge configuration cannot deploy the authenticated Next.js server, media processing and Wallet workers. Decide a supported Node/`sharp` host or design/test a complete dynamic Edge adapter; do not merge to the old Cloudflare static deployment.

## Porting order and boundaries

1. **Visual identity without insecure state (started here):** carry original files from `public/brand/`, token palette and `StampyLogo` into the secure running app, preserve optional phone photo + private print flow and Supabase/Google accounts. Global branding is **stampy.** next to the editable venue identity; no sample visits/photos are minted.
2. **Append-only database adaptation:** draft new `00007+` migrations against STAMPY's *actual* six-migration schema. Replace permissive policies, keep existing rows, add staff-confirmed/idempotent visits, private owner-linked photos, locked keepsakes, customer account settings and connector isolation. Back up first. A phone in `00004_customer_accounts.sql` is RLS-isolated but **not encrypted** by that SQL; decide whether application/column encryption is additionally required.
3. **Route adapters:** preserve the STAMPY kiosk, POS, photobooth and admin UI while replacing browser ledgers and service-role ID-based POSTs with server-verified routes. Reuse the secure branch's consent and pass state machines, not the STAMPY public `wallet_pass_links` API. Screen content is reauthorized on every refresh and denied if permission is revoked or unknown.
4. **Regression gates:** run the unchanged STAMPY test suite *and* new PGlite security/integration tests on the combined code, fix legacy tests whose expectations contradict server authority (do not silently remove them), then typecheck, lint, build, Supabase staging migrations/OAuth/Storage and real-device Wallet/printing QA. Baseline lint already fails: do not report it green until addressed.

**Scope of this step:** authentic brand assets and presentation are ported onto the secure branch. This is not a complete merge of the STAMPY branch, not a migration to STAMPY's database, and not a production deployment. The upstream STAMPY screens/tests remain untouched until their server contracts can be ported safely.
