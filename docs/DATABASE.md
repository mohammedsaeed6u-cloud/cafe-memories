# قاعدة البيانات

الترحيلات مصدر الحقيقة: `supabase/migrations/00001_initial_schema.sql` ثم `00002_product_refactor.sql` ثم `00003_secure_core.sql` ثم `00004_customer_accounts.sql` ثم `00005_visit_keepsakes.sql`. الأنواع في `src/types/database.ts` تُولد من الترحيلات بواسطة `corepack pnpm db:types`؛ **لا تُعدّل الأنواع يدويًا**.

يدعم النطاق الحالي المنشآت والفروع وعضويات الموظفين والضيوف وزياراتهم وصورهم وموافقات العرض وقواعد/أحداث المكافآت ورموز QR واقتران الشاشات. عند فتح الضيف صفحة الفرع، يسجّل `check_in_customer` حضورًا صالحًا ساعتين؛ هذا ليس إثبات شراء. `record_verified_visit` وحدها توثّق الشراء بعد تحقق الموظف، و`attach_verified_visit_memory` تضع صورة اختيارية واحدة على ختم موجود دون سكّ زيارة جديدة. `keepsake_cards` تحفظ تاريخ وعتبة ومكافأة كل دورة زيارات عند اكتمالها، ويُخصم أقدم كارت مؤهل ذريًا بواسطة `redeem_customer_reward` ويرتبط بحدث الصرف. يقرأ `get_keepsake_balance` رصيد الكروت للـAPI المخوّل بدل إعادة تقسيم جميع الزيارات على عتبة قد تتغير لاحقًا.

يجب تطبيق الترحيل على قاعدة متوقفة عن كتابات النسخة القديمة وبعد فحص تعارض البيانات. راجع [دليل النشر والترحيل](DEPLOYMENT_AND_DATA_MIGRATION.md). اختبارات PGlite تُغطي RLS ودوال SQL لكنها لا تحاكي Supabase Auth/Storage الحقيقيين أو التنازع متعدد الاتصالات.
